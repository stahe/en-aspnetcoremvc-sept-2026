    9. Layered Architecture and Data Access

    The previous examples kept their data in memory. A real application stores it in a database and is organized into layers (see the diagram in the introduction):

    • the web layer (controllers, views): read the request, call the business layer, select the view;
    • the business layer: business rules;
    • the DAO ([Data Access Object]) layer: database queries.

    Each layer is aware only of the layer below it, and as few details about it as possible: the web layer is unaware of SQL, and the business layer is unaware of HTML. This separation makes each layer easier to understand, test, and evolve. Example 28 applies this to managing a list of people: it is, on a smaller scale, the management of doctors and clients from the case study.

    Database access is handled by Entity Framework Core (EF Core), the ORM ([Object-Relational Mapper]) of [.NET]: it maps [C#] classes (the entities) to the database tables, translates queries written in [LINQ] into SQL, and transforms the retrieved rows into objects. EF Core communicates with each database type via a provider ([provider]): for [MySQL], the [NuGet] package, which includes [Pomelo.EntityFrameworkCore.MySql], which in turn includes the EF Core and the [MySqlConnector] driver.

// a row of the [persons] table

public class Person
{
    // the primary key: an integer key is, by convention, generated by the database

    [Column("version")]
    [ConcurrencyCheck]
    public int Version { get; set; } = 1;

    [Column("first_name")]
    [MaxLength(30)]
    public string FirstName { get; set; } = "";

    [Column("last_name")]
    [MaxLength(30)]
    public string LastName { get; set; } = "";

    [Column("age")]
    public int Age { get; set; }
}
    • line 7: the class [Person] corresponds to the table [persons]: each row of the table will be a [Person] object;
    • Lines 12–14: the primary key ([[Key]]). [[Column]] specifies the column name corresponding to each property;
    • lines 18–19: the version column. [[ConcurrencyCheck]] instructs EF Core to add the condition [AND version = <value read>] to each [UPDATE]: this is the optimistic lock, explained further below;
    • line 22: the other columns. [[MaxLength]] specifies the column size.

    using Example28.Entities;
using Microsoft.EntityFrameworkCore;

namespace Example28.Data;

// the DbContext: the connection to the database, and the tracking of the entities read
public class PersonsDbContext(DbContextOptions<PersonsDbContext> options) : DbContext(options)
{
    // the "table" of persons: it is queried with LINQ
    public DbSet<Person> Persons => Set<Person>();

    // just before each save: the version of every MODIFIED person
    // is increased by 1. The generated UPDATE compares the OLD value:
    //   UPDATE persons SET ..., version = 2 WHERE id = 1 AND version = 1
    public override Task<int> SaveChangesAsync(bool acceptAllChangesOnSuccess, CancellationToken cancellationToken = default)
    {
        foreach (var entry in ChangeTracker.Entries<Person>())
        {
            if (entry.State == EntityState.Modified)
            {
                entry.Entity.Version++;
            }
        }
        return base.SaveChangesAsync(acceptAllChangesOnSuccess, cancellationToken);
    }
}
    • line 7: DbContext is the central object of EF Core. It represents a work session with the database: it opens connections, sends queries, and tracks the entities it has read (it knows which ones have been modified);
    • Line 10: A [DbSet<Person>] represents the table: it is queried using [LINQ], and entities are added to it;
    • Lines 15–24: [SaveChangesAsync] sends all pending changes to the database. It is redefined to increment the version number for each modified person. [ChangeTracker] tracks the changes: for each tracked entity, it knows its status ([Added], [Modified], [Deleted], [Unchanged]). EF Core, unlike [TypeORM], does not manage an integer version column on its own: it is up to us to increment it.

    using Example28.Data;
using Example28.Entities;
using Microsoft.EntityFrameworkCore;

namespace Example28.Dao;

// the DAO layer: queries, no business rule
public class PersonsDao(PersonsDbContext db)
{
    // SELECT ... FROM persons ORDER BY last_name, first_name
    public Task<List<Person>> ListAsync() =>
        db.Persons.AsNoTracking().OrderBy(p => p.LastName).ThenBy(p => p.FirstName).ToListAsync();

    // SELECT ... FROM persons WHERE id = @id LIMIT 1; null if missing
    public Task<Person?> ReadAsync(int id) =>
        db.Persons.FirstOrDefaultAsync(p => p.Id == id);

    // a person with the same first and last names, other than [exceptId]
    public Task<Person?> NamesakeAsync(string firstName, string lastName, int exceptId) =>
        db.Persons.FirstOrDefaultAsync(p => p.FirstName == firstName && p.LastName == lastName && p.Id != exceptId);

    // INSERT if the person is new (Id = 0), UPDATE of the modified columns otherwise
    public async Task<Person> SaveAsync(Person person)
    {
        if (person.Id == 0)
        {
            db.Persons.Add(person);
        }
        await db.SaveChangesAsync();
        return person;
    }

    // DELETE FROM persons WHERE id = @id, without reading the person first
    public Task DeleteAsync(int id) =>
        db.Persons.Where(p => p.Id == id).ExecuteDeleteAsync();
}
    • line 8: DAO receives [DbContext] via injection;
    • Lines 11–12: A [LINQ] request, translated to SQL by EF Core. Nothing is sent to the database before the call to [ToListAsync], which executes the query and returns the list. [AsNoTracking()] indicates that these entities will not be modified: [DbContext] does not need to track them;
    • lines 15–16: the first function that checks the condition, or [null];
    • Lines 19–20: A person with the same first and last name, other than [exceptId]: useful for modifying a record, which must not conflict with itself. The comparison is performed by [MySQL], so according to the database’s collation: without regard to uppercase letters or accents;
    • Lines 23–30: A new person ([Id] set to 0) is added to [DbSet]; [SaveChangesAsync] then creates a [INSERT] and re-reads the identifier assigned by the database. A person read by this same [DbContext] and modified is detected by change tracking: [SaveChangesAsync] creates a [UPDATE] containing only the modified columns;
    • Lines 34–35: [ExecuteDeleteAsync] sends a [DELETE] directly to the database, without reading the records first.

    The DAO layer contains no rules: only queries. These methods are asynchronous ([Task], [async] / [await]): while the database is processing, the thread is freed up and serves other requests.

    using Example28.Dao;
using Example28.Data;
using Example28.Entities;
using Microsoft.EntityFrameworkCore;
using MySqlConnector;

namespace Example28.Business;

public record PersonData(string FirstName, string LastName, int Age);

// the BUSINESS layer: the business rules, and only them
public class PersonsBusiness(PersonsDao dao, PersonsDbContext db)
{
    private const string Namesake = "A person already has these first and last names.";

    public Task<List<Person>> ListAsync() => dao.ListAsync();

    public async Task<Person> ReadAsync(int id) =>
        await dao.ReadAsync(id) ?? throw new BusinessException("This person does not exist (anymore).");

    public Task<Person> AddAsync(PersonData data) =>
        TransactionAsync(async () =>
        {
            // rule 1: no two persons with the same first and last names
            if (await dao.NamesakeAsync(data.FirstName, data.LastName, 0) is not null)
            {
                throw new BusinessException(Namesake);
            }
            var person = new Person { FirstName = data.FirstName, LastName = data.LastName, Age = data.Age };
            return await dao.SaveAsync(person);
        });

    public Task<Person> EditAsync(int id, int version, PersonData data) =>
        TransactionAsync(async () =>
        {
            var person = await ReadAsync(id);
            // rule 2: we do not modify a record modified meanwhile by someone else
            if (person.Version != version)
            {
                throw new BusinessException("This record has been modified meanwhile: reload it.");
            }
            if (await dao.NamesakeAsync(data.FirstName, data.LastName, id) is not null)
            {
                throw new BusinessException(Namesake);
            }
            person.FirstName = data.FirstName;
            person.LastName = data.LastName;
            person.Age = data.Age;
            return await dao.SaveAsync(person);
        });

    public async Task<Person> DeleteAsync(int id)
    {
        var person = await ReadAsync(id);
        await dao.DeleteAsync(id);
        return person;
    }

    // [work] runs inside a transaction: COMMIT if it succeeds, ROLLBACK
    // if it throws an exception. The database errors become BusinessExceptions
    private async Task<R> TransactionAsync<R>(Func<Task<R>> work)
    {
        await using var transaction = await db.Database.BeginTransactionAsync(); // START TRANSACTION
        try
        {
            var result = await work();
            await transaction.CommitAsync(); // COMMIT
            return result;
        }
        catch (DbUpdateConcurrencyException)
        {
            // the UPDATE "WHERE id = ... AND version = ..." modified no row
            throw new BusinessException("This record has been modified meanwhile: reload it.");
        }
        catch (DbUpdateException e) when (e.InnerException is MySqlException { ErrorCode: MySqlErrorCode.DuplicateKeyEntry } sqlError
                                          && sqlError.Message.Contains("unq_persons_first_name_last_name"))
        {
            // two simultaneous additions: the uniqueness constraint of the database rejected the second
            throw new BusinessException(Namesake);
        }
        // any other exception goes on its way; the transaction, closed
        // without COMMIT by "await using", is cancelled (ROLLBACK)
    }
}

    Let’s break down this code:

    • line 9: a person’s data, as transmitted by the web layer;
    • line 12: the business layer uses DAO and [DbContext] to open transactions. Both are [Scoped] services: during a request, the DAO and the business layer receive the same [DbContext], and therefore the same connection and the same transaction. (With [TypeORM], the transaction object had to be passed to each method of DAO);
    • lines 18–19: An absent person is a [BusinessException]. The [??] operator provides a replacement value; [throw] can serve as a substitute;
    • lines 21–30: the addition, within a transaction. Rule: no two people may have the same first and last names. This is checked before the write to display a clear message;
    • lines 33–49: the update. Additional rule: the optimistic lock (lines 38–40). The update form retrieved the record’s version as it was when the form was opened. If it has changed in the meantime (another user has modified the same record), the update is rejected rather than silently overwriting the user’s work;
    • lines 61–67: [BeginTransactionAsync] opens a transaction ([START TRANSACTION]), and [CommitAsync] commits it ([COMMIT]). [await using] closes the transaction upon exiting the block, no matter what happens: if closed without [COMMIT], it is rolled back ([ROLLBACK]). Thus, an exception thrown by [work] (including a [BusinessException]) rolls back everything that has been done;
    • lines 70–73: the version check mentioned earlier is not always sufficient: two users can save the same record at the same time, and both pass the check. The second user’s [UPDATE ... WHERE id = ... AND version = ...] then does not modify any lines; EF Core detects this and raises a [DbUpdateConcurrencyException], which becomes the same [BusinessException];
    • Lines 75–79: Similarly, two simultaneous additions by the same person pass the homonym check, but the database’s uniqueness constraint does not allow them to be added. The error [MySQL] (code [DuplicateKeyEntry], No. 1062) occurs nested within a [DbUpdateException] (property [InnerException]); its message includes the name of the constraint. The clause [when] intercepts the exception only if the condition is true. [is MySqlException { ErrorCode: ... } sqlError] is a pattern filter: it tests the type and value of a property and stores the object in a variable.

namespace Example28.Controllers;

// the WEB layer: it only knows the business layer
public class PersonsController(PersonsBusiness business) : Controller
{
    [HttpGet("/")]
    public IActionResult Home() => RedirectToAction(nameof(List));

    [HttpGet("persons")]
    public async Task<IActionResult> List()
    {
        return View(await business.ListAsync());
    }

    [HttpGet("persons/add")]
    public IActionResult AddForm() => Form(BuildView("Add a person", "/persons/add", new()));

    [HttpPost("persons/add")]
    public async Task<IActionResult> Add(PersonForm input)
    {
        var view = BuildView("Add a person", "/persons/add", input);
        if (!ModelState.IsValid)
        {
            return Form(view);
        }
        try
        {
            var person = await business.AddAsync(new PersonData(input.FirstName!, input.LastName!, input.Age!.Value));
            TempData["Success"] = $"{person.FirstName} {person.LastName} has been added.";
            return RedirectToAction(nameof(List));
        }
        catch (BusinessException e)
        {
            // a business rule refuses: we display the form again, the message at the bottom of the page
            return Form(view, e.Message);
        }
    }

    [HttpGet("persons/{id:int}/edit")]
    public async Task<IActionResult> EditForm(int id)
    {
        try
        {
            var p = await business.ReadAsync(id);
            var values = new PersonForm { FirstName = p.FirstName, LastName = p.LastName, Age = p.Age, Version = p.Version };
            return Form(BuildView("Edit a person", $"/persons/{id}/edit", values));
        }
        catch (BusinessException e)
        {
            TempData["Error"] = e.Message;
            return RedirectToAction(nameof(List));
        }
    }

    [HttpPost("persons/{id:int}/edit")]
    public async Task<IActionResult> Edit(int id, PersonForm input)
    {
        var view = BuildView("Edit a person", $"/persons/{id}/edit", input);
        if (!ModelState.IsValid)
        {
            return Form(view);
        }
        try
        {
            var data = new PersonData(input.FirstName!, input.LastName!, input.Age!.Value);
            var person = await business.EditAsync(id, input.Version ?? 0, data);
            TempData["Success"] = $"{person.FirstName} {person.LastName} has been edited.";
            return RedirectToAction(nameof(List));
        }
        catch (BusinessException e)
        {
            return Form(view, e.Message);
        }
    }

    [HttpPost("persons/{id:int}/delete")]
    public async Task<IActionResult> Delete(int id)
    {
        try
        {
            var person = await business.DeleteAsync(id);
            TempData["Success"] = $"{person.FirstName} {person.LastName} has been deleted.";
        }
        catch (BusinessException e)
        {
            // no form to display again: the error also travels in TempData
            TempData["Error"] = e.Message;
        }
        return RedirectToAction(nameof(List));
    }

    // the model of the form view, with the ModelState errors sorted by field
    private FormView BuildView(string title, string action, PersonForm values) => new()
    {
        Title = title,
        Action = action,
        Values = values,
        Errors = ModelState
            .Where(c => c.Value!.Errors.Count > 0)
            .ToDictionary(c => c.Key, c => c.Value!.Errors[0].ErrorMessage, StringComparer.OrdinalIgnoreCase),
    };

    private ViewResult Form(FormView view, string? error = null)
    {
        ViewData["Error"] = error;
        return View("Form", view);
    }
}
