    7. The lifecycle of a request

    Between the arrival of a request and the execution of the action, [ASP.NET Core] involves several types of objects, each with a specific role. We have already encountered some of them: middleware ([UseStaticFiles], [UseRequestLocalization], the middleware from Example 23), and the model binding ([IModelBinder], Example 12). The MVC component adds filters that run around the action. The case study uses each of them:

    Object
    Role
    In the case study
    middleware
    Prepares the request; does not yet know the action
    static files, language, authentication (reading the token), error pages
    authorization filter
    allow or deny access to the action
    [[Authorize]], [[Authorize(Roles = ...)]]
    Template binding
    Convert and validate parameters
    forms, [ModelState]
    action filter
    Code before and after the action
    (not used: services and the view parent class are sufficient)
    exception filter
    Convert an exception into a response
    Session expired: redirect to /login

    namespace Exemple24.Filtres;

// a middleware class: it receives the rest of the pipeline
// (next) in its constructor, and processes each request in InvokeAsync
public class JournalMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext contexte)
    {
        Console.WriteLine();
        Console.WriteLine($"--- {contexte.Request.Method} {contexte.Request.Path}{contexte.Request.QueryString}");
        Console.WriteLine("1. middleware (avant)");
        await next(contexte); // the entire rest of the pipeline: routing, filters, action, view
        Console.WriteLine($"8. middleware (après : code {contexte.Response.StatusCode})");
    }
}
    • Line 5: A middleware can be a class. Its constructor takes a [RequestDelegate]: the rest of the pipeline (the subsequent middlewares, followed by MVC);
    • line 7: the [InvokeAsync] method is called for each request;
    • line 12: the middleware calls the rest of the pipeline and waits for it to finish. If it did not call it, the request would stop there (it would then have to generate the response itself). The code placed before this call executes on the outbound request, and the code placed after it executes on the return: the middleware “wraps” everything else and sees the final status code of the response.

    using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.Controllers;
using Microsoft.AspNetCore.Mvc.Filters;

namespace Exemple24.Filtres;

// an AUTORISATION filter: it determines whether the action can be executed.
// It is also an attribute: it is applied to a controller or an action.
public class BloquerAttribute : Attribute, IAuthorizationFilter
{
    public void OnAuthorization(AuthorizationFilterContext contexte)
    {
         // The filter knows the target action, unlike middleware
        var action = (ControllerActionDescriptor)contexte.ActionDescriptor;
        Console.WriteLine($"2. filtre d'autorisation (action visée : {action.ActionName})");
        if (contexte.HttpContext.Request.Query.ContainsKey("bloquer"))
        {
             // Setting `Result` short-circuits the rest of the process: no binding, no action
            contexte.Result = new StatusCodeResult(StatusCodes.Status403Forbidden);
        }
    }
}
    • line 9: an authorization filter implements [IAuthorizationFilter]. The class also derives from [Attribute]: it can be applied, in square brackets, to a controller or an action;
    • lines 14–15: Unlike middleware, the filter knows the target action ([ActionDescriptor]). This is what allows the [[Authorize(Roles = "ADMIN")]] attribute (see the next chapter) to protect only certain actions;
    • lines 16–19: A filter rejects the request by setting [contexte.Result]: the sequence (binding, action) is not executed, and this result becomes the response. Here, a 403 response (access denied), with no content.

    using Microsoft.AspNetCore.Mvc.ModelBinding;

namespace Exemple24.Filtres;

// Model binding for an integer parameter (see Example 12)
public class EntierBinder : IModelBinder
{
    public Task BindModelAsync(ModelBindingContext contexte)
    {
        var valeur = contexte.ValueProvider.GetValue(contexte.ModelName).FirstValue;
        Console.WriteLine($"3. liaison de modèle (valeur reçue : \"{valeur}\")");
        if (int.TryParse(valeur, out var entier))
        {
            contexte.Result = ModelBindingResult.Success(entier);
        }
        else
        {
            contexte.ModelState.AddModelError(contexte.ModelName, $"\"{valeur}\" n'est pas un nombre entier.");
        }
        return Task.CompletedTask;
    }
}

    A custom template binding, like those in Example 12. An invalid value does not stop anything: the error is logged in [ModelState], and the action determines the outcome (line 18).

    using System.Diagnostics;
using Microsoft.AspNetCore.Mvc.Filters;

namespace Exemple24.Filtres;

// an ACTION filter: code before and after the action.
// ActionFilterAttribute: a framework class, whose useful methods are redefined
public class ChronoAttribute : ActionFilterAttribute
{
    private const string Cle = "chrono";

    public override void OnActionExecuting(ActionExecutingContext contexte)
    {
         // The action’s parameters are already bound: the filter can read them
        Console.WriteLine($"4. filtre d'action (avant ; paramètres : {string.Join(", ", contexte.ActionArguments.Values)})");
        contexte.HttpContext.Items[Cle] = Stopwatch.StartNew();
    }

    public override void OnActionExecuted(ActionExecutedContext contexte)
    {
        var chrono = (Stopwatch)contexte.HttpContext.Items[Cle]!;
         // contexte.Exception: any exception thrown by the action
        var issue = contexte.Exception is null ? "" : $", exception {contexte.Exception.GetType().Name}";
        Console.WriteLine($"6. filtre d'action (après, {chrono.ElapsedMilliseconds} ms{issue})");
    }
}
    • line 8: an action filter. [ActionFilterAttribute] is a framework class that already implements the necessary interfaces: we override ([override]) the relevant methods;
    • Lines 12–16: [OnActionExecuting] runs before the action. Model binding has already taken place: the action parameters are available ([ActionArguments]). A timer is started ([Stopwatch]), stored in [HttpContext.Items] (query scope; see Chapter 6);
    • lines 19–24: [OnActionExecuted] runs after the action. If the action threw an exception, it is available in [contexte.Exception]. An action filter can also override the result of the action ([contexte.Result]).

    using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.Filters;
using Microsoft.AspNetCore.Mvc.ModelBinding;
using Microsoft.AspNetCore.Mvc.ViewFeatures;

namespace Exemple24.Filtres;

// an EXCEPTIONS filter: it transforms an exception into a response
public class PageErreurFilter(IModelMetadataProvider metadonnees) : IExceptionFilter
{
    public void OnException(ExceptionContext contexte)
    {
        Console.WriteLine($"x. filtre d'exceptions ({contexte.Exception.GetType().Name} : {contexte.Exception.Message})");
         // Instead of the default error page, our Error view is displayed, with status code 500
        contexte.Result = new ViewResult
        {
            ViewName = "Erreur",
            StatusCode = StatusCodes.Status500InternalServerError,
            ViewData = new ViewDataDictionary(metadonnees, contexte.ModelState) { Model = 500 },
        };
        contexte.ExceptionHandled = true; // The exception is handled: it does not propagate further up the chain
    }
}
    • Line 9: An exception filter implements [IExceptionFilter]. It receives exceptions thrown by the model binding, the action filters, and the action. This is a service: it receives the [IModelMetadataProvider] object via injection, which is necessary to construct the [ViewData] dictionary for a view;
    • lines 15–20: instead of the default error page, the filter generates a HTML page: the [Erreur] view, with status code 500. This is what the [View] method of a controller does, written here by hand;
    • Line 21: The exception is marked as handled; it does not propagate further up the chain.

    using System.Text.Encodings.Web;
using System.Text.Unicode;
using Exemple24.Filtres;
using Microsoft.Extensions.FileProviders;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews(options =>
{
     //: a GLOBAL filter: it applies to all actions in the application
    options.Filters.Add<PageErreurFilter>();
});
builder.Services.AddSingleton(HtmlEncoder.Create(UnicodeRanges.All));

var app = builder.Build();

// The middleware runs in the order in which it is added
app.UseMiddleware<JournalMiddleware>();
// an error response SANS with content (400, 403, 404...): the request is re-executed
// request with the URL /error/{code}, which generates a page
app.UseStatusCodePagesWithReExecute("/erreur/{0}");
app.UseStaticFiles(new StaticFileOptions
{
    FileProvider = new PhysicalFileProvider(Path.GetFullPath(Path.Combine(builder.Environment.ContentRootPath, "..", "commun", "bootstrap"))),
    RequestPath = "/bootstrap",
});

app.MapControllers();
app.Run();
    • line 10: a global filter is applied to all actions in the application. It is added to the options of MVC;
    • line 17: a class-based middleware is added via [UseMiddleware]. Middlewares execute in the order they are added: this one is first, so it processes all requests;
    • line 20: a framework middleware. When an error response (codes 400–599) has no content, it re-executes the request using the address [/erreur/{code}] (where [{0}] is replaced by the code), and returns the resulting page while retaining the error code. This is how 403 responses from the authorization filter, 400 responses from the action, and 404 responses from routing become HTML pages.

    using Exemple24.Filtres;
using Microsoft.AspNetCore.Mvc;

namespace Exemple24.Controllers;

// Two filters set on the controller: they apply to all of its actions
[Bloquer]
[Chrono]
public class CalculController : Controller
{
    [HttpGet("carre/{n}")]
    public IActionResult Carre([ModelBinder(typeof(EntierBinder))] int n)
    {
        Console.WriteLine($"5. action Carre({n}) ; modèle valide : {ModelState.IsValid}");
        if (!ModelState.IsValid)
        {
            return BadRequest(); // A 400 with no content: see UseStatusCodePagesWithReExecute
        }
        if (n == 13)
        {
            throw new InvalidOperationException("13 porte malheur"); // an “unexpected” error
        }
        return View("Resultat", n * n);
    }
}
    • lines 7–8: two filters applied to the controller; they apply to all of its actions (they can also be applied to a single action);
    • line 12: the custom parameter binding;
    • lines 15–17: an invalid parameter: a 400 response with no content;
    • lines 19–21: an “unexpected” error, to see the exception filter in action.

    using Microsoft.AspNetCore.Mvc;

namespace Exemple24.Controllers;

public class ErreurController : Controller
{
     // [Route] without the HTTP method: the re-executed request retains its original method

        return View("Erreur", code);

}
    • line 8: the action for the error page. [[Route]], without a method; HTTP, accepts all methods: a re-executed POST request remains a POST request;
    • Line 12: The page retains the original error code.

    This log shows:

    • the order of the steps: middleware, authorization filter, model binding, action filter (before), action, action filter (after), and then the middleware again, which sees the final response code;
    • the authorization filter that rejects the request bypasses the rest of MVC (no binding, no action);
    • an invalid parameter does not prevent the action from executing: the action itself decides, based on [ModelState] (see example 09);
    • an exception from the action is handled by the exception filter, which generates the response;
    • an empty error response (400, 403, 404) is converted into a page by re-executing the request (step 7). For an unknown address, MVC does not even come into play: no route matches.

    The case study combines these mechanisms: [UseStatusCodePagesWithReExecute("/erreur/{0}")] and a controller ([ErreurController]) for 400, 403, and 404 pages; the [UseExceptionHandler("/erreur/500")] middleware, which similarly re-executes any request that ends with an unhandled exception; and an exception filter ([Web/HtmlExceptionFilter.cs]) for a specific case: an expired session does not display an error page but redirects to the login page.
